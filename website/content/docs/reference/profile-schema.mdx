A **Machine Profile** is the source-owned declaration of desired configuration.
A **Profile Revision** is an immutable, validated, signed publication of that
profile. JSONC authoring layout and comments do not affect the canonical digest.

## Profile shape

The v2 authoring contract contains a stable profile ID, display name, Follower
Groups, Profile Resources, and an optional default schedule:

```jsonc
{
  "id": "workstation",
  "version": 2,
  "name": "Developer workstation",
  "groups": [
    { "name": "developers", "description": "Developer tools" }
  ],
  "resources": [],
  "scheduleDefault": {
    "type": "daily",
    "at": "00:00",
    "timezone": "local"
  }
}
```

`scheduleDefault` is optional and is a default a Follower Machine *inherits*,
not a resource a profile applies. A profile that omits it schedules nothing.

Only daily and weekly calendars in the follower's own timezone are accepted,
written as `"timezone": "local"`. Those are the only shapes every follower
backend can render: launchd and Windows Task Scheduler refuse a custom
expression and cannot bind a named timezone, so publishing either left those
followers with no scheduled synchronization at all. A follower that wants a
backend-specific calendar or a named timezone sets one locally with
`canonfig schedule set --timezone`, where only that machine has to render it.

A Follower Machine owns its own native synchronization job. `canonfig schedule
set` and `canonfig schedule remove` decide it, and that decision outlives an
apply. Canonfig installs the inherited default only when the follower has not
decided for itself, and it reconciles that job after a converged run rather
than as part of one, so a machine whose scheduler does not work still
converges.

Canonfig normalizes omitted defaults and unordered collections before hashing.
It rejects duplicate IDs, missing dependencies, dependency cycles, undeclared
groups, invalid targets, incompatible policies, and incompatible verification.

## Resource kinds and defaults

| Kind | Desired outcome | Default Apply Policy |
| --- | --- | --- |
| `file` | Exact regular-file content and mode, or raw symlink target | `replace` |
| `directory` | A source-owned tree with explicit directories and modes | `mirror-owned` |
| `config` | Declared keys in TOML, JSON, or YAML | `merge` |
| `skill` | A canonical skill tree | `replace-if-unmodified` |
| `tool` | Installed and verified executable capability | `ensure` |
| `credential` | Usable local credential reference | `require-local` |

Under `merge`, a key Canonfig owned that the profile no longer declares is
removed from the follower's file. A key the follower claimed through its Local
Overlay stays, which is how an operator keeps a key the profile has dropped.

`replace` on a directory is a true mirror: the whole directory is listed, and
entries Canonfig never wrote are removed so the managed subtree ends up exactly
the desired subtree. `mirror-owned` is the policy that preserves foreign
entries. Parent directories required by desired files remain even when the
profile does not list those directories explicitly.

A `tool` may declare `agentInstall`, which is what permits a bounded
Configuration Agent to install it:

```jsonc
{
  "kind": "tool",
  "toolId": "example",
  "recipes": [],
  "agentInstall": {
    "paths": ["~/.local/share/canonfig/tools/example"],
    "origins": ["https://registry.npmjs.org"]
  }
}
```

`paths` says where the agent may write and `origins` which exact HTTPS origins
it may fetch from. Both are authored and never inferred. A tool with no usable
recipe and no `agentInstall` is reported as Human Action Required rather than
handed to an agent, because an Agent Task with no writable path and no origin
cannot install anything.

Under `replace-if-unmodified`, a missing target is reinstalled: absence is not a
local edit, so there is nothing to overwrite. A target that exists but cannot be
verified is reported rather than overwritten.

Every Profile Resource has a unique ID, kind, target, kind-specific
specification, verification contract, optional groups, and optional
dependencies. Dependencies form a directed acyclic graph.

## Filesystem fidelity

File, directory, and skill resources preserve numeric modes. Directory and
skill resources can also declare empty directories. A symlink target remains
the exact authored string, so a relative target stays relative to the link:

```jsonc
{
  "id": "tools",
  "kind": "directory",
  "target": "~/.local/tools",
  "spec": {
    "kind": "directory",
    "mode": 493, // 0755
    "directories": [
      { "path": "cache", "mode": 488 } // 0750
    ],
    "files": [
{ "path": "current", "content": "", "symlinkTo": "../bin/tool" }
    ]
  },
  "verify": { "method": "digest", "digest": "<directory-digest>" }
}
```

JSON numbers are decimal. The comments above show their octal permission forms.

## Apply Policies

- **`replace`** records rollback material and atomically replaces an owned
  target where the platform supports that filesystem operation.
- **`mirror-owned`** adds and updates desired files, then removes only files
  previously owned by Canonfig and still unmodified.
- **`merge`** updates declared keys through a format-aware codec while
  preserving the **Local Overlay**.
- **`replace-if-unmodified`** writes only when current content matches the
  Applied Resource Record or already matches desired content.
- **`append-local`** puts Source text first and preserves follower-local text
  after it. Only regular, non-executable UTF-8 text files support this policy.
- **`ensure`** reaches and verifies a capability without removing unrelated
  software.
- **`require-local`** verifies a local credential reference and otherwise
  produces Human Action Required.

<Callout title="Transfer is not apply" type="info">
  Content-addressed transfer decides which blobs must cross the source boundary.
  The resource's Apply Policy independently decides how those bytes may affect
  Observed State.
</Callout>

### Keep local instructions with `append-local`

Use `"policy": "append-local"` on a `file` resource such as `AGENTS.md`. Keep
the file's normal `spec.content` and digest verification: that digest identifies
the Source text, not the combined follower file. Existing policies do not change.

Canonfig writes this layout:

```md title="Follower AGENTS.md"
<!-- canonfig:source:start -->
Source instructions
<!-- canonfig:source:end -->

Follower-local instructions
```

Edit local instructions below the closing marker. On first adoption, Canonfig
preserves a differing existing file in full as local text. If it exactly matches
Source, Canonfig adds the markers without duplicating the text. A missing file
starts with no local additions. Make a backup before choosing a new policy.

Later syncs replace only the Source section. They preserve local text, including
its whitespace and line endings, and do not append another copy. Changing or
removing an existing Source section produces drift; move intentional edits below
the closing marker before syncing. Malformed or repeated markers require manual
repair. Deleting the whole file allows Canonfig to recreate the Source section.

Removing the resource from the profile removes only its unchanged Source section
and leaves local text in place, or an empty file if there is none. A later failure
restores the full backup only if the file still matches the action's expected
output. If you edit it after the write, rollback stops and retains the backup
under the machine's Canonfig cache at `rollback/<run-id>/` for manual recovery.
Successful runs remove rollback backups; these are not a long-term file archive.
Avoid saving the file while a sync is writing it. Canonfig checks for changed
content before replacing a file, but it does not lock external editors.

Source content cannot contain these reserved markers or NUL characters, and
symlinks and executable files cannot use this policy.

This is text composition, not a semantic merge. A differing file adopted for the
first time can contain older shared rules as well as local rules. Canonfig does
not guess which to discard or which conflicting instruction takes precedence.
Review that local text once; it remains follower-owned and is never uploaded.

## Verification

The v2 contract supports digest, command, executable-present,
credential-present, and symlink verification. Allowed methods depend on resource
kind. Verification is mandatory after mutation, including after agent apply.

## Applied Resource Records

An **Applied Resource Record** stores the exact resource revision, digest,
mode, raw symlink target, and owned tree entries that Canonfig last applied.
This record enables safe mirror deletion, mode-aware drift detection, audit,
and recovery. It is not a Local Overlay and does not confer source authority on
the follower.
